# 第 18 章：沿 Agentgateway 源码追踪一次模型与工具请求

前面用 Python 实验把流、尝试、准入和结算拆开了。现在换一个真实工程：团队准备让多个应用共享模型入口，并把两个 MCP 工具服务器接到同一个地址。接入时要回答的仍是同一组问题：谁决定路由，权限在哪一跳检查，失败后哪些动作可能再次发生，日志里的费用依据是什么。

本章核对 Agentgateway 提交 `1785d189bbbd29bc87630030c3c3e1c91fda694e`，读取日期为 2026-10-25。来源编号为 [S11](91-sources.md)。下面的架构结论来自此版本的源码和仓库文档；本章未运行其二进制、真实供应商或 Kubernetes 集群，也没有将这些代码阅读结论计入本书 Python 实验的通过项。复核其他版本时，先重新定位文件和调用关系。

## 18.1 先分清数据面、控制面与界面

Agentgateway 的 Rust 数据面负责实际连接、请求策略、后端选择和协议处理。Go 控制面负责将 Kubernetes 资源转换为配置并通过 xDS 下发，也包含部署管理。React 界面调用管理接口，提供模型、工具、策略、日志和费用等操作入口。

独立部署可以使用本地 YAML，不依赖 Kubernetes 控制面。界面资源可以在构建时嵌入二进制；界面可用与否，不决定上游协议是否兼容。

| 阅读入口 | 要追踪的责任 |
| --- | --- |
| `crates/agentgateway-app/src/lib.rs` | 参数、配置来源和进程初始化 |
| `crates/agentgateway/src/app.rs` | 工作池、客户端、状态管理器和服务组装 |
| `crates/agentgateway/src/proxy/` | HTTP、TCP 与连接处理 |
| `crates/agentgateway/src/llm/` | 模型路由、网关策略和价格目录 |
| `crates/llm/src/` | 供应商适配、消息与流式转换 |
| `crates/agentgateway/src/mcp/` | MCP 聚合、会话和协议处理 |
| `controller/pkg/agentgateway/translator/` | Kubernetes 资源翻译 |
| `ui/src/pages/` | 管理与调试界面 |

这个划分能帮助定位故障。资源修改后数据面没有变化，先查翻译、下发和实际生效配置；模型回答字段丢失，先查输入格式识别和转换；工具越权则要沿身份、目标选择与工具授权分别检查。不要用重启整个系统代替确定故障所属阶段。

## 18.2 两条配置路径进入同一套运行时模型

仓库 `architecture/configuration.md` 区分静态配置、本地动态配置和 xDS 配置。线程、管理地址等进程设置在启动阶段读取；路由、后端和策略可以来自本地动态配置或远程控制面。

本地配置经解析和转换进入内部表示，状态管理器监听文件变化。xDS 使用项目自己的 protobuf 资源，也映射到共享内部表示。这里使用的是 xDS 传输机制，不能据此把数据面理解成 Envoy；资源定义位于 `crates/protos/proto/resource.proto`。

配置设计尽量保持资源粒度：路由引用所属监听器，策略保留所附着的目标，运行时负责优先级与合并。其目的包括避免修改一条路由或策略时，重新下发整个大型配置集合。这是资源建模选择，不能直接推出任何环境下的更新吞吐数字。

对于第 16 章的配置审计要求，还需区分三个事实：文件已写入、配置已被接受、当前请求采用了哪一份配置。源码中有重新加载状态和管理查询相关实现；这些入口可帮助检查实际生效状态，但不自动等于每条请求都记录了可重放的完整配置快照。

建议准备一个专门的配置变更用例：先让有效配置正常服务，再写入无效字段，核对加载错误、继续服务的实际配置与观测信息。测试前写出预期，运行后保存证据。本章没有实跑该用例。

## 18.3 沿请求主链路追踪策略

从 `proxy/gateway.rs` 进入连接处理，再看 `proxy/httpproxy.rs` 的 `proxy`、`proxy_internal`、`attempt_upstream` 等函数。路由选择逻辑还会进入 `http/route.rs`，上游请求通过客户端与后端传输实现发送。

为了阅读，可以把链路画成：接收连接，匹配监听器和路由，执行适用策略，选择后端，执行后端处理，发送上游，处理响应，完成观测。它只是阅读索引；不同协议和策略有不同阶段，实际顺序必须沿函数调用核对。

策略目录中能找到 JWT、API Key、OAuth/OIDC、外部授权、限流、转换、超时、重试和预算等实现。存在一个策略模块只能证明实现入口存在，不能证明部署已经启用，也不能说明它对所有请求生效。

例如，一条拒绝规则究竟在上游连接之前执行，还是只过滤上游返回的工具列表，影响完全不同。验证时要同时观察客户端结果和上游接收次数。后者可以揭示“用户看见拒绝，但敏感请求已经发送”的问题。

## 18.4 模型别名、能力与转换分开检查

当前版本的 `examples/llm-basic/config.yaml` 用 `llm.models` 声明模型。下面保留其别名映射结构，以占位值代替实际模型名：

```yaml
llm:
  port: 4000
  models:
  - name: smart
    provider: openAI
    params:
      model: REPLACE_WITH_VERIFIED_MODEL
      apiKey: $OPENAI_API_KEY
```

这段配置展示的是模型名映射与凭据引用，尚未运行。占位模型必须替换为账号可用且经过验证的实际模型；环境变量展开方式应按固定版本核对。不要把示例别名当成质量、能力或价格保证。

`crates/agentgateway/src/llm/` 处理网关侧模型路由与策略；`crates/llm/src/` 包含 OpenAI、Anthropic、Gemini、Vertex、Bedrock 等适配器及转换逻辑。阅读某个跨协议请求时，应继续追踪输入识别、供应商请求构建、普通响应转换和流式转换，而不是在模型选择处停止。

仓库说明了保留未知 JSON 字段的解析方式：只对需要操作的部分建立字段，其余数据保留，必要时再转换成更完整的类型。这有助于透传兼容。跨供应商转换时，仍要判断源字段在目标协议中是否有对应语义；保存了字段不等于另一家供应商会执行它。

| 用例 | 应分别核对 |
| --- | --- |
| 普通文本 | 请求模型、实际上游模型、返回文本与结束原因 |
| 工具调用 | 工具名、参数增量、调用标识与返回关联 |
| 推理内容 | 内容与签名如何保留，目标是否接受 |
| 多模态 | MIME、URI、编码与目标模型能力 |
| 流式输出 | 分片顺序、终止、错误和 usage 的到达时机 |

供应商转换的 golden tests 可以检验完整输入输出映射；事件顺序、半途中断与取消则还需要流或状态机测试。这些测试属于不同证据，不能相互替代。

## 18.5 有重试实现，还要证明允许再次执行

在真实网关里可以找到超时、重试、故障转移和异常实例驱逐的代码。评估时应把第 7 章的问题带进去：一次调用失败后，系统掌握了什么事实，是否已经发送请求体，是否已经对下游提交结果，是否可能产生工具副作用或费用。

只观察客户端一次成功，会漏掉多次上游调用。应让替身为每次接收生成记录，并关联入口请求与 attempt。分别注入连接前失败、请求已接收后无响应、首段文本后断流，以及完整输出后 usage 缺失，再检查调用次数和用户看到的终态。

上面的故障分类是一份待执行验收方案，不是对这个版本默认重试行为的断言。项目存在重试策略，并不能证明它采用本书替身的“未开始”合同；本书的 `trust_not_started` 也不能直接移植为真实供应商配置。方法语义和可重复执行依据仍需回到 [S01](91-sources.md)。

## 18.6 MCP 聚合增加了两层权限问题

仓库支持一个下游入口连接多个上游 MCP 服务。聚合除了转发，还涉及初始化、协议协商、会话、资源与工具的合并以及通知处理。所选版本的 MCP README 还讨论了不同协议代际的协商方式；这属于该实现的版本行为，不能概括成所有 MCP 客户端与服务器的共同保证。

其中一个有用的区分是目标条件和资源授权。目标上的 `condition` 可以利用认证上下文决定哪些上游参与虚拟 MCP 请求；`mcpAuthorization` 则用于上游响应后的具体工具或其他资源授权。两者的时机与保护对象不同。

设想租户 north 只允许访问工具服务器 A。仅把 B 的工具从列表隐藏，还不够证明 B 从未被初始化，也不够证明直接调用已知工具名会被拒绝。至少应检查：

1. 目标筛选后，B 是否收到初始化或发现请求。
2. 列表是否只包含获准资源。
3. 客户端绕过列表直接调用时，权限是否再次检查。
4. 身份切换、会话复用或权限撤销后，旧状态是否造成越权。

MCP stdio 目标还意味着网关会启动工具进程，部署者需要治理命令、运行身份和环境变量。允许调用工具也不等于工具动作可以撤销；业务写入、审批和补偿仍需执行宿主提供合同。

## 18.7 CEL 的表达能力与上下文成本

Agentgateway 使用 CEL 表达授权、日志属性、转换和限流维度。例如仓库给出的授权思路可以表示为：

```cel
jwt.sub == "test-user" && mcp.tool.name == "add"
```

表达式依赖所处阶段的上下文。响应尚未到来时，没有可用的响应变量；请求体已被消费后，若后续日志还需要它，就必须提前保留。

`architecture/cel.md` 说明了配置解析时分析依赖、请求执行时按需保存数据的设计。这样可以减少不使用请求体的策略所承担的复制成本。文档同时指出依赖识别有表达式写法限制，所以新增表达式应验证变量可用性与实际结果。

这也把第 11 章的内容采集问题变成资源问题：新增一个正文日志字段，可能增加请求体保存、内存占用和敏感数据留存。评审日志配置时，应该同时看采集目的、字段依赖、体积边界和清理期限。

## 18.8 费用页面与结算证据之间还缺什么

源码包含模型价格目录、用量处理、预算策略，以及日志存储和费用分析界面。这些能力使网关具备费用治理入口；价格目录有版本、模型名有映射、usage 有来源和完整性，仍需逐项核对。

| 观察到的实现 | 还需验证的合同 |
| --- | --- |
| 模型价格目录 | 价格生效时间、计价单位、缓存及推理用量口径 |
| 预算拒绝 | 多副本争用、预留时机、取消与崩溃后的处理 |
| 日志数据库 | 写入失败、重启恢复和重复终态处理 |
| 费用图表 | 未知用量是否单列、估算与账单是否区分 |

数据库可以保存管理配置或请求日志，但仅凭“使用了数据库”不能推出存在跨副本原子预算账本。评估预算实现应继续读 `http/budget/` 及其调用链，再用第 16 章的竞争和崩溃用例验证。这里不对未检查的事务语义作结论。

本书实验的一 credit 是 UTF-8 字节；真实服务中的 token、请求费和其他费用维度需要另建合同。不要将实验余额与网关费用页面上的金额直接比较，也不要把缺失 usage 的请求按零费用处理。

## 18.9 交付一份可以继续复核的接入记录

先固定源码提交和构建工具版本，再记录配置、模型协议、启用策略、故障用例和结果。工具链以仓库的 `rust-toolchain.toml`、`go.mod`、`ui/package.json` 为准；开发说明中的最低版本可能落后于当前配置。

可以先读代码与现有测试，再用本地 HTTP 替身验证路由和故障行为；需要真实供应商语义时，使用受控测试账号单独验收。Kubernetes 接入还要增加资源翻译、下发失败、配置生效和滚动排空用例。没有运行的用例写为待验证，不填通过。

**练习：** 选择“north 可访问 A、不可访问 B，且流中断后不静默换模型”这个接入目标。交付源码定位表、最小配置设计和故障矩阵。为每个结论注明“源码观察”“文档说明”或“运行证据”，并分别记录客户端结果、上游接收次数与用量状态。指出哪一项结论仍不能证明远端停止计费或工具动作已撤销。
